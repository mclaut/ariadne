# Ariadne v0.8.23

Full recovery sets now follow the same single-generation rule as collection
snapshots: retain one last verified full copy, expire the previous one only
after the replacement has passed an independent recovery test.

## Full backup and recovery

- `ariadnectl backup-full` reads a private, explicit `~/.ariadne/full-backup.json`
  plan. It captures fresh verified snapshots of the configured collections,
  installed programs, declared sources and model dependencies, online SQLite
  copies, bounded append-only log prefixes, and only Ariadne-owned client sections.
- With this plan installed, ordinary `backup` and due automatic maintenance
  backups create a full set too. Without a plan, collection-only backup behavior
  is unchanged; shared models, credentials and other projects are never guessed.
- All captured entries are copied into a separate recovery directory and compared
  by type, mode, link target and SHA-256. The copied Qdrant restores and reads every
  point; SQLite passes integrity checks; configured Git repositories pass fsck.
  Captured model blobs are checked against their manifest digests, and an isolated
  copied Ollama runtime produces a finite embedding of the configured dimension.
- Only after these checks does `backups/previous/full` replace the older generation.
  Corruption, a missing source, failed recovery, or a modified/in-use previous copy
  blocks unsafe cleanup. Failed derivative workspaces remain for diagnosis.

## Audit remains available

Before retiring a full set, its access/activity history and recovery receipts are
independently copied and verified under `backups/full-audit`. Existing audit data
and audit directories are never rotated. Historical recovery states outside the
audit scope expire when their verified replacement is published.

Legacy timestamped full sets require explicit enrollment by exact directory name,
manifest filename and SHA-256. Their entire immutable inventory must still match;
unknown directories and altered copies are left untouched.

See [the full backup plan](../backup-full.md) for setup and recovery boundaries.

## Platform and migration verification

- Windows SQLite drive paths use an authority-free `file:///C:/...` URI.
- Legacy full manifests are compared in the same canonical path order; traversal order cannot misclassify an unchanged full set.
- Cleanup can resume against an already restored, immutable full keeper with `backup-full --retry-cleanup`.
- Release publication waits for native Windows tests as well as Linux verification.

Windows durability checks open the newly created SQLite copy with a write-capable handle before flushing. Native Windows, Linux and site CI passed for the final implementation before this version-only release commit. Full-backup operations have a one-hour command allowance when a full plan is present.
